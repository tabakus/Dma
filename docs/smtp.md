# SMTP-интеграция: состояние, требования, план проверки

Заявки отправляются преподавателю по SMTP собственным клиентом. Это утверждённая часть архитектуры.

**SMTP-интеграция не готова к эксплуатации.** Провайдер, адреса отправителя и получателя,
реквизиты не выбраны (`docs/open-questions.md`, В-1…В-3). Реальная отправка писем ещё не проверялась.

## 1. Что реализовано

| Часть | Файл |
| --- | --- |
| SMTP-клиент на стандартных Web API (TextEncoder, btoa), без модулей Node.js | `server/smtp/client.ts` |
| Подключение через TCP/TLS-сокеты Cloudflare (`connect()` из `cloudflare:sockets`) | `server/smtp/cloudflare-socket.ts` |
| Режимы: порт **465** с TLS сразу (`SMTP_SECURITY=tls`) и порт **587** со STARTTLS (`SMTP_SECURITY=starttls`). Порт 25 не поддерживается | `server/smtp/client.ts`, `server/application/config.ts` |
| Аутентификация AUTH PLAIN, при её отсутствии AUTH LOGIN | `server/smtp/client.ts` |
| Один отправитель, один получатель, письмо `text/plain` UTF-8 | `server/application/email.ts` |
| Общий таймаут отправки 15 с; ошибка на любом этапе = заявка не принята (502) | `server/smtp/client.ts`, `server/application/handler.ts` |
| Проверка конфигурации: все переменные заданы, допустимы только пары 465 + `tls` и 587 + `starttls` | `server/application/config.ts` |

Не реализовано и не входит в текущий объём: OAuth2 (XOAUTH2), несколько получателей,
вложения, HTML-письма.

Почему свой клиент: Nodemailer и большинство Node.js SMTP-библиотек используют модули
`net`/`tls`, которых в Workers Runtime нет. При разработке рассматривался пакет `worker-mailer`;
он не используется, клиент проекта не имеет внешних зависимостей.

## 2. Что проверено на имитации SMTP-сервера

Тесты `tests/smtp.test.ts` (запуск: `npm test`) используют SMTP-сервер в памяти, без сети:

- порт 465: EHLO → AUTH PLAIN → MAIL FROM → RCPT TO → DATA → QUIT;
- порт 587: EHLO → STARTTLS → повторный EHLO → AUTH;
- отказ, если сервер на 587 не предлагает STARTTLS (пароль при этом не отправляется);
- AUTH LOGIN, если AUTH PLAIN недоступен;
- неверный пароль (535) → ошибка на этапе `auth`, письмо не отправлено;
- отказ сервера после DATA → ошибка, успех не засчитывается;
- ошибка на QUIT после принятого письма сбоем не считается;
- таймаут при молчащем сервере;
- экранирование строк, начинающихся с точки.

Кроме того, функция `functions/api/application.ts` собирается в бандл, в котором из внешних модулей
импортируется только `cloudflare:sockets` (модулей Node.js нет).

### Локальная проверка в workerd (15.11.2026)

`wrangler pages dev` (Wrangler 4.156.1) с фиктивным SMTP-сервером без TLS — подробности
в `docs/cloudflare-deployment.md`:

- `connect()` из `cloudflare:sockets` устанавливает соединение; приветствие, EHLO и команда STARTTLS проходят.
- Порт 465 при недоступном сервере: ответ 502 `delivery_failed` за доли секунды (в логе этап `unknown`, П-3).
- **Ошибка П-1:** при сбое TLS-рукопожатия после STARTTLS запрос зависает — после срабатывания
  таймаута не завершается закрытие сокета. Исправление предложено и проверено на временной копии,
  в код не внесено (вопрос В-19).

## 3. Что ещё предстоит проверить с реальным провайдером

До проверки нужно согласовать и внести исправление П-1 (В-19).

- Работа `cloudflare:sockets` в Cloudflare Pages Functions с выбранным SMTP-сервером.
- TLS-рукопожатие и проверка сертификата сервера провайдера (465 и/или 587).
- Формат приветствия, EHLO и списка AUTH именно у этого провайдера.
- Допускает ли провайдер подключения из IP-адресов Cloudflare.
- Доставка: письмо не попадает в спам, кириллица и умлауты в теме и теле отображаются верно,
  Reply-To ведёт на адрес посетителя.

## Секреты

- Реквизиты задаются только в переменных окружения Cloudflare Pages
  (Settings → Variables and Secrets), отдельно для Production и Preview.
- `SMTP_PASSWORD` — только тип **Secret** (зашифрованная переменная).
- В исходном коде, `wrangler.toml` и репозитории реквизитов нет. Для локальной проверки —
  файл `.dev.vars` (в `.gitignore`) по образцу `.dev.vars.example`, где только заглушки на домене `.invalid`.

Переменные: `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURITY`, `SMTP_USERNAME`, `SMTP_PASSWORD`,
`MAIL_FROM`, `MAIL_TO`, `ALLOWED_ORIGINS`. Описание — в `README.md`, порядок добавления —
в `docs/cloudflare-deployment.md` (рекомендуется тип Secret для всех).

## Требования к провайдеру

| Требование | Почему |
| --- | --- |
| SMTP с аутентификацией AUTH PLAIN или AUTH LOGIN | Клиент поддерживает только эти механизмы |
| Порт 465 (TLS сразу) или 587 (STARTTLS) | Порт 25 в Cloudflare закрыт и не используется |
| Сертификат TLS от публичного центра сертификации | Нужен для защищённого соединения из Cloudflare |
| Отдельный SMTP-пароль или пароль приложения | Не использовать основной пароль ящика |
| Ящик отправителя на домене сайта, настроенные SPF/DKIM/DMARC | Иначе письма будут попадать в спам |
| Возможность заключить договор обработки данных (AVV/DPA) | В письме персональные данные (DSGVO, см. В-9) |
| Подключения из IP-адресов Cloudflare не блокируются | Некоторые провайдеры ограничивают облачные сети |

## План проверки после выбора провайдера

Не выполнялся: провайдер и реквизиты не выбраны.

1. Создать тестовый ящик или пароль приложения у выбранного провайдера.
2. Локально: `.dev.vars` с реквизитами → `npm run build` → `npx wrangler pages dev dist`
   → отправить форму на тестовой странице продукта. Ожидается письмо и ответ `{ ok: true }`.
3. Проверить оба режима, если провайдер их поддерживает (465/`tls` и 587/`starttls`).
4. Негативные проверки: неверный пароль → ответ 502 `delivery_failed`, в логах Cloudflare
   только `{"event":"delivery_failed","stage":"auth","code":"535"}`, без персональных данных.
5. Preview-деплой Cloudflare Pages с переменными Preview → та же проверка уже в Cloudflare
   (подтверждает работу `cloudflare:sockets` с этим провайдером).
6. Проверить доставку: письмо не в спаме, кириллица и умлауты в теме и теле отображаются верно,
   Reply-To ведёт на адрес посетителя.
7. Записать результат в этот файл и закрыть вопросы В-1…В-3 и В-11 в `docs/open-questions.md`.
